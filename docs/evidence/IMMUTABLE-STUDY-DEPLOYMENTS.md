# Immutable Study Deployments

## Status

**IMPLEMENTED deployment contract once this change is merged.**

Real-world retention, barcode, visual-recognition and OCR studies must not depend on the moving GitHub Pages routes that follow every `main` deployment.

A study baseline is therefore published under an immutable versioned path:

> `/shopping-budget-companion/study/<baseline>/`

The source is not rebuilt during study publication. The publisher reuses the exact `pages-site` artifact from a completed successful `Quality` run on `main`.

## Why

The moving routes:

- `/qa/`
- `/beta/`
- `/cohort/`
- `/barcode-benchmark/`
- `/barcode-paired-analyzer/`
- `/ocr-paired-analyzer/`
- `/visual-recognition-benchmark/`
- `/shelf-label-ocr-benchmark/`
- `/shelf-label-ocr-tesseract-benchmark/`

are useful for current validation, but their embedded `buildRevision` changes whenever a newer `main` commit is deployed.

A multi-day or multi-week human study needs one stable executable surface whose code revision cannot silently change during recruitment or follow-up.

## Build contract

Guarded evidence builds use a relative Vite base.

That means the exact tested artifact can be served from either:

> `/shopping-budget-companion/beta/`

or:

> `/shopping-budget-companion/study/<baseline>/beta/`

without redirecting asset requests back to the moving route.

CI rejects guarded `index.html` files that contain an absolute `/shopping-budget-companion/...` asset base.

The public production PWA is unchanged and continues to use its normal repository base.

## Publication workflow

Use:

> GitHub Actions → **Publish Study Baseline** → Run workflow

Inputs:

1. `baseline`
   - lowercase URL-safe slug;
   - example: `evidence-baseline-2026-09-25-r9`;
   - once published, the same slug cannot be reused or overwritten.

2. `quality_run_id`
   - the run ID of a completed successful **Quality** workflow triggered by a push to `main`.

3. `source_sha`
   - exact lowercase 40-character Git SHA for that Quality run.

The workflow verifies that the selected run:

- is named `Quality`;
- was triggered by `push`;
- ran on `main`;
- completed successfully;
- has exactly the supplied source SHA.

It then downloads that run's already-tested `pages-site` artifact.

No application rebuild occurs during study publication.

The `pages-site` artifact is currently retained for 3 days, so publish the baseline before that exact Quality run artifact expires. If it has expired, create a new successful main Quality run and use a new baseline/source pair rather than rebuilding an old study revision out of band.

## Published structure

Example:

```text
study/evidence-baseline-2026-09-25-r9/
├── index.html
├── study-baseline.json
├── qa/
├── beta/
├── cohort/
├── barcode-benchmark/
├── barcode-paired-analyzer/
├── ocr-paired-analyzer/
├── visual-recognition-benchmark/
├── shelf-label-ocr-benchmark/
└── shelf-label-ocr-tesseract-benchmark/
```

`study-baseline.json` records:

- baseline slug;
- exact source SHA;
- exact Quality run ID.

Evidence JSON generated by the copied study surfaces still carries the embedded `buildRevision` from the original tested build.

## Immutability rule

Publishing fails if `study/<baseline>/` already exists.

A new revision requires a **new baseline slug**.

Never replace, edit, retarget or delete an active or completed study baseline merely to make its evidence match newer code.

If a defect invalidates a study executable:

1. stop collecting new evidence on that baseline;
2. preserve existing files for audit;
3. fix the defect through the normal PR/Quality path;
4. publish a new baseline slug from a new successful main Quality run;
5. analyze the revisions separately.

## Production deployment preservation

The normal `main` Pages deployment still replaces the moving public/guarded surfaces with the newly tested artifact.

Before that replacement, it copies the existing `study/` tree from `gh-pages`.

Before push, the deployment compares the preserved study Git tree hash with the staged study tree hash.

If they differ, deployment fails.

Therefore ordinary product releases cannot silently rewrite an existing study baseline.

## Required human-study rule

Once evidence collection begins, study instructions must cite:

- immutable study URL;
- baseline slug;
- exact source SHA.

Do not instruct participants to use the moving `/beta/`, `/qa/` or benchmark routes for a cohort that is intended to remain revision-stable.

Do not combine evidence from different `buildRevision` values into one interpreted cohort unless the owning evidence protocol explicitly defines a cross-version analysis.

## Relationship to `study/*` Git refs

Git refs and deployed study URLs solve different problems:

- `study/*` refs preserve source-code provenance;
- `/study/<baseline>/` preserves the executable Pages surface.

For strongest auditability, both should identify the same source SHA.

Repository rules for protecting `study/*` refs remain tracked separately by governance issue #58.
